# HELIX applicability to a system library

The user authorized a targeted workflow extension if needed. No HELIX fork is
needed to extract this repository: existing genesis, architecture, contract,
test-plan and concern workflows can describe library consumers and API outcomes.
The installed concern-resolution guidance explicitly recognizes libraries and
excludes them from automatic admin-console selection.

A useful future HELIX change is a library framing variant shared by genesis,
vision and Frame, rather than a second public skill or duplicate artifact graph.
It should replace product-market assumptions with consuming systems, supported
APIs/runtimes, compatibility policy, extension ownership, source preservation,
conformance corpus and distribution/release evidence. Reuse the existing design
and verification authority hierarchy and retain optional business context.

Acceptance examples should include both umf.visual and the dashboard/native-BI
pattern: generic core capabilities remain upstream, while native libraries own
qualified interpretation, exact retention and independent lifecycle. A library
variant must not require hosted operations, UI, commercial personas or invented
market metrics. Unknown compatibility is recorded rather than assumed.

This is a recorded proposal, not an implemented HELIX capability or new marker
field. The repository uses the existing catalog and labels its library context
in AGENTS, vision, architecture and concerns. The next Frame pass can expose
concrete friction before an upstream methodology change is justified.
