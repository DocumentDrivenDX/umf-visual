# TD-093: Visual vocabulary extension

## Scope

Implement `umf.visual` 1.0.0 as CONTRACT-083 defines it: package, payload schema, semantic
validation, typed TypeScript API, the example set and tests. Rendering is out of scope.

## Technical Approach

Register one vocabulary at document scope, following TD-077 (dashboard). One payload per
document keeps identity simple: the visual's id is the document's subject, and every item id
lives in one namespace, so a walkthrough step can focus any item without a sort qualifier.

The payload schema checks shape: closed enums, required fields, id pattern, one value key per
comparison value. It does not set `additionalProperties: false`; the semantic walker reports
unknown keys as `VISUAL_UNKNOWN`, as the dashboard walker does. Rules that depend on the kind
or on other items (form membership, kind blocks, references, cycles, form rules, dates and
values) are semantic, so each failure has its own code rather than a generic structure error.

Composition advice (`VISUAL_DENSITY`) is computed outside the registry. Core sets `complete`
false on any diagnostic, so emitting density as a warning would make ordinary 8–15 node
visuals uneditable.

## Component Changes

### New: `spec/extensions/visual/`

`package.json` (scopes `["document"]`, semantic validation, evidence
`tests/visual/vocabulary.test.ts`) and the identical standalone `schema.json`.

### New: `src/extensions/visual/index.ts`

Types, the kind-to-forms table, the semantic validator and the API. Form rules are one table
of functions keyed by form, so adding a form is a schema enum change, a table row and a test.

### Modified: `src/index.ts`

Exports the extension.

### New: `fixtures/visual/`

`inventory/`: one JSON document per visuals-inventory row with a target kind, derived from
HELIX's `architecture-model.toml` and from `sources/`, a fictional example system (Beacon, a
support desk's reply drafter: its architecture model, migrations, CI workflows, ticket states
and estate) that stands in for the inventory's pilot system (source path and digest recorded).
Rows whose target is "embed X" reuse X and have no document of their own; rows that stay
tables have none. `forms/`: one document per form the inventory does not exercise. Both sets
are built by `~/Documents/visuals/build-umf-visual-fixtures.py` (outside this repository,
because it reads the HELIX checkout) and checked in as data.

### Modified: audit fixtures and the acceptance ledger

Regenerated by `test:schemas` and `scripts/acceptance-traceability.ts`.

## API/Interface Design

CONTRACT-083 §API. Names mirror the dashboard extension (`inspect…`, `read…Document`,
`write…Document`, `get…`, `edit…`).

## Data Model Changes

None to core.

## Integration Points

`@ux-builder/visuals` imports the types and `inspectVisual`; documentor writes documents and may
check structure with `schema.json`.

### External Dependencies

None added.

## Security

Payloads are untrusted data. Validation runs no code from the document; evidence paths are
retained and never opened.

## Performance

Validation is linear in items, plus cycle walks bounded by node count (≤ 15 for graph kinds).

## Testing

`tests/visual/vocabulary.test.ts`: every fixture round-trips and is complete (AC1); a mutation
table checks each code independently (AC2); unknown fields (AC3); atomic edits (AC4); advice
(AC5). The package and schema audits must pass.

## Migration & Rollback

New vocabulary; removing it touches no other extension.

## Implementation Sequence

1. Schema and package. 2. Semantics and API. 3. Fixtures. 4. Tests and audits. 5. Ledger.

## Risks

Renderers may need fields M3 reveals; those are minor versions. The id pattern admits
underscores, which the PRD's `[a-z0-9-]+` did not; architecture-model ids require them.
